# Подготовка к защите СРО2

Демо-сценарий, подготовка ноутбука, вероятные вопросы с ответами и шпаргалка с числами. Презентация —
`docs/deliverables/Презентация_СРО2.pptx` (12 слайдов, заметки докладчика с таймингом, всего 7 минут).

## 1. Ноутбук для защиты (за день до)

1. `git pull`, затем `make images-save` — сборка образов и сохранение в `bioauth-images.tar` (нужен интернет один раз).
2. Проверка без сети: выключить Wi-Fi → `make down` → `make up-offline` → `make health`. Если образы удалялись —
   `make images-load` перед `make up-offline`.
3. Открыть <http://localhost:3000> в Chrome, разрешить камеру для `localhost`. Камера и passkey работают только на
   localhost или по HTTPS — проектор с другим адресом не подойдёт, демонстрировать с самого ноутбука.
4. Войти как `admin` и зарегистрировать passkey в «Профиль → Безопасность» (Touch ID / Windows Hello) — без него действия с политиками недоступны.
5. Заранее зарегистрировать себя как субъекта (`/enroll`) при хорошем освещении — на защите останется только вход.
6. Положить рядом: `examples/scores-demo.csv`, распечатанное собственное фото (для атаки), запасной PDF презентации.
7. Прогнать сценарий из раздела 2 **три раза подряд** без ошибок (критерий приёмки #8). Если что-то упало — `make logs`.

Резерв: если Docker на ноутбуке не запускается, показывать PDF презентации и снимки экранов из
`docs/deliverables/screenshots` (v1) и `screenshots/v2`.

## 3. Вероятные вопросы и ответы

**Почему не EER?** EER уравнивает доли ошибок, а не их цену. При c_FA/c_FR = 10 выгодно поднять порог: FAR падает
с 1,79 % до 0,52 %, FRR растёт до 6,2 %, а ожидаемые потери E снижаются на 41,8 %. Порог совпадает с EER только при
равных стоимостях и равных разбросах оценок.

**Откуда 41,8 %, если в статье 41 %?** В статье числа округлены. Точный расчёт при N(0,72; 0,09) и N(0,30; 0,11) даёт
E(τ_EER) = 0,196509 и E(τ\*) = 0,114387, то есть 41,8 %. Значения сверены со SciPy до 10⁻¹².

**Почему линеаризация точная, а не приближённая?** Для правила «И» FAR набора = ∏FARᵢ, поэтому
ln FAR = Σ xᵢ·ln FARᵢ — это тождество для бинарных xᵢ, а не разложение в ряд. Ограничение FAR ≤ FAR_max становится
линейным без потери точности. FRR = 1 − ∏(1 − FRRᵢ) тоже логарифмируется точно; приближение Σ FRRᵢ из статьи
программа не использует.

**Как доказывается оптимум ЦЛП?** Целевая функция E нелинейна. Решатель обходит фронт Парето по (ln FAR, ln(1 − FRR))
методом ε-ограничений: каждое решение ЦЛП (HiGHS) даёт кандидата и нижнюю границу E для оставшейся области. Когда
нижняя граница не меньше лучшего найденного E, оптимум доказан — в примере статьи за 2 итерации. Совпадение с полным
перебором проверяется property-тестами на случайных задачах.

**Что будет при n > 20?** Полный перебор (2ⁿ наборов) ограничен 20 факторами; при «Автоматически» включается ЦЛП —
до 50 факторов, с доказательством оптимума, но без полного рейтинга всех наборов.

**Чем подтверждена точность?** 103 теста ядра: числа статьи, 50 эталонов SciPy, хвосты распределений до 10⁻¹⁹⁸,
property-тесты; всего 290 автоматических тестов; CI на каждый push поднимает систему в Docker и прогоняет e2e.

**Где SOLID?** S — ядро отделено от фреймворков, один use case — один класс; O — v2 калибрует порог тем же сценарием
v1 без изменения ядра; L — оба решателя реализуют один интерфейс и взаимозаменяемы; I — узкие порты
(`ScoreSamplesReader`, `PolicyReader`); D — модули зависят от портов (`FACE_ENGINE`, `AUDIT_LOG`), реализации
подставляются через DI, поэтому в тестах bio-engine заменяется поддельным сервером.

**Где FSD?** Слои app → pages → widgets → features → entities → shared, импорт только вниз и только через `index.ts`
слайса; правило проверяет steiger в CI. Пример: страница «Калибровка» собирается из фичи `calibrate-threshold`,
виджетов графиков и сущности `calibration`.

**Как защищены биометрические данные?** Кадры обрабатываются в памяти и не сохраняются; шаблон — AES-256-GCM с
отменяемой ортогональной проекцией (ISO/IEC 24745); отзыв согласия удаляет шаблон и passkey; журнал аудита с цепочкой
хэшей; отсутствие биометрии в логах проверяется тестом.

**Можно ли обойти проверку фотографией или видео?** Фото не выполняет команды; видео не знает случайных команд
заранее; модель MiniFASNet отсекает экран и печать. Ограничение: маски и инъекция видеопотока не испытывались —
это указано в ограничениях.

**Зачем OpenID Connect, а не свой API входа?** Стандарт понимают готовые библиотеки любого языка; приложение получает
подписанный ID-токен с тем, как проверен пользователь (`amr`, `acr`), и не касается биометрии. PKCE защищает публичные
клиенты от перехвата кода, ротация refresh-токенов — от кражи долгоживущего токена (ADR-0018).

**Что будет, если администратор отключит пользователя?** Сессии завершаются, refresh-токены приложений отзываются,
обмен кода и userinfo отклоняются; уже выданный токен доступа живёт не дольше 10 минут.

**Почему порог не меняется автоматически?** Атакующий, влияющий на выборку, мог бы сдвинуть порог в свою пользу.
Решение о риске принимает администратор, и оно фиксируется в журнале аудита (ADR-0015).

**Хватит ли данных для FAR 10⁻⁵?** Нет: по правилу трёх нужно ≥ 300 000 сравнений злоумышленников без ложных
допусков. Интерфейс показывает, какой FAR реально подтверждён; для малых FAR — пакетный режим на открытом наборе.
