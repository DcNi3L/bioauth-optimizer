# ADR-0005. PostgreSQL + Prisma; Redis и RabbitMQ не используются

**Статус:** Принято · **Дата:** 04.11.2026

## Контекст
Пользователь предложил PostgreSQL, Redis и RabbitMQ «если будет нужда». Что нужно хранить: каталоги факторов, загруженные наборы оценок, историю экспериментов. Профиль нагрузки: все расчёты синхронные и быстрые (параметрический порог < 50 мс, ЦЛП при n ≤ 20 < 2 с, CSV 10⁶ строк < 3 с), пользователей единицы, вход в систему не требуется.

## Решение
- **PostgreSQL 16 + Prisma** — единственное хранилище. Prisma выбрана за типобезопасный клиент, декларативную схему и миграции.
- **Redis — не используется.** Кэшировать нечего: расчёт дешевле сетевого запроса к кэшу. Повторный одинаковый вход определяется по `input_hash` в Postgres. Сессий нет.
- **RabbitMQ — не используется.** Нет длительных или фоновых задач, нет других потребителей событий. Очередь добавила бы контейнер, повторы, идемпотентность и статус задачи без какой-либо пользы.
- **Аутентификации пользователей нет**: однопользовательский учебный прототип, запускается локально.

## Когда пересмотреть (триггеры)
| Триггер | Что добавить |
|---|---|
| Появились задачи > 5 с (байесовская оптимизация гиперпараметров, n > 50, NSGA-II на больших каталогах) | RabbitMQ + воркер + таблица `job` со статусами; API возвращает 202 и `jobId` |
| Многопользовательский режим | Аутентификация (OIDC), владелец у экспериментов, проверка доступа в каждом запросе |
| Тяжёлые повторяющиеся запросы к истории при большом числе пользователей | Сначала индексы и пагинация в Postgres; Redis — только если измерения покажут необходимость |

## Последствия
- (+) Три контейнера вместо пяти, меньше точек отказа; проще защищать и демонстрировать.
- (+) Решение обратимо: модули обращаются к хранилищу через порты.
- (−) Если на защите спросят «почему без Redis/RabbitMQ» — ответ в этом ADR: нет нагрузки, которую они решают.
