# ADR-0002. Математика — отдельный чистый TypeScript-пакет

**Статус:** Принято · **Дата:** 04.11.2026

## Контекст

Корректность расчётов — главный критерий (35 баллов, NFR-1/2). Если математика размазана по контроллерам и сервисам NestJS, её сложно тестировать изолированно и легко сломать при правке инфраструктуры.

## Решение

Пакет `@bioauth/optimization-core` содержит все формулы и алгоритмы из 02-mathematical-model. Ограничения:

- нет зависимостей от `@nestjs/*`, `next`, `react`, драйверов БД, HTTP, `process.env`, файловой системы;
- функции детерминированы, возвращают неизменяемые объекты результатов;
- внешние зависимости: `@stdlib/math-base-special-*` (спецфункции) и `highs` (MILP), причём `highs` подключается только через интерфейс `MilpPort`.

## Альтернативы

- *Писать ядро на Python (SciPy, OR-Tools CP-SAT) как отдельный сервис* — ближе к инструментам, названным в СРО1, но это второй язык, второй контейнер и межсервисный протокол. Всё нужное (erfc, MILP) доступно в Node. Отклонено для v1; Python-воркер предусмотрен для класса 2 в v2 (08-roadmap).
- *Логика внутри сервисов NestJS* — отклонено по причинам выше.

## Последствия

- (+) Тесты ядра выполняются за секунды без БД и HTTP; покрытие ≥ 95 %.
- (+) Ядро можно опубликовать как самостоятельную библиотеку или вызвать из CLI.
- (−) Выбор доменных типов требует аккуратности: DTO из `contracts` маппятся в типы ядра в слое application.
