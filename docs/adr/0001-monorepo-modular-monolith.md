# ADR-0001. Монорепозиторий pnpm + Turborepo, модульный монолит

**Статус:** Принято · **Дата:** 04.11.2026

## Контекст

Один разработчик, срок 11 дней, нужны фронтенд (Next.js) и бэкенд (NestJS) с общими типами и общей математикой. Нагрузка — единицы пользователей.

## Решение

Один репозиторий: `apps/web`, `apps/api`, `packages/optimization-core`, `packages/contracts`, `packages/config`. Менеджер пакетов — **pnpm workspaces** (строгая изоляция зависимостей, быстрый install), оркестратор задач — **Turborepo** (кэш сборки и тестов, `turbo prune` для Docker). Бэкенд — один процесс NestJS, разделённый на модули с явными границами (модульный монолит).

## Альтернативы

- _Микросервисы_ (отдельный сервис расчётов): сетевые вызовы, отдельные деплои и контракты без какой-либо выгоды при такой нагрузке. Отклонено.
- _Два отдельных репозитория_: дублирование типов и схем валидации, рассинхронизация. Отклонено.
- _Nx_: мощнее, но тяжелее в настройке; Turborepo достаточно. Отклонено.

## Последствия

- (+) Изменение контракта видно сразу и фронтенду, и бэкенду; одна команда `pnpm test`.
- (+) Расчётный модуль при необходимости выносится в отдельный сервис без переписывания, потому что ядро уже изолировано (ADR-0002).
- (−) Нужна дисциплина границ — она закреплена линтерами (03-architecture §3.4).
