# ADR-0011. Доступ к БД: Kysely + pg и SQL-миграции вместо Prisma

**Статус:** Принято · **Дата:** 04.11.2026 · **Заменяет часть ADR-0005** (выбор ORM; решение «PostgreSQL, без Redis и RabbitMQ» остаётся в силе)

## Контекст

ADR-0005 предполагал Prisma. При реализации выяснилось:

- Prisma скачивает нативные движки (`binaries.prisma.sh`) при `generate` и `migrate`. В закрытых сетях (песочница разработки, корпоративный прокси, офлайн-защита) сборка падает, а миграции нельзя проверить на реальной базе.
- Схема Prisma не умеет выражать CHECK-ограничения (`far > 0 AND far < 1`, длина bytea = count·8), которые docs/05 требует закрепить в БД. Их всё равно пришлось бы писать вручную в SQL.
- Репозитории тонкие: четыре таблицы, без сложных связей, так что сильные стороны Prisma здесь почти не нужны.

## Решение

- **Kysely 0.28** — типобезопасный конструктор SQL поверх драйвера **pg**. Типы таблиц описаны в `apps/api/src/shared/database/schema.ts`.
- **Миграции — обычные SQL-файлы** в `apps/api/migrations/NNNN_name.sql`. Их применяет небольшой мигратор (`migrator.ts`): по порядку, каждый файл в своей транзакции, под advisory lock, с учётом в таблице `schema_migrations`. Только вперёд.
- Seed предустановленного каталога СРО1 выполняется идемпотентно после миграций (`migrate.cli.ts`).
- Репозитории реализуют те же порты (DIP), поэтому смена ORM не затронула use cases.

## Альтернативы

- *Prisma* — см. контекст. Отклонено.
- *TypeORM / MikroORM* — тяжёлые ORM с декораторами-сущностями; для четырёх таблиц избыточно. Отклонено.
- *Drizzle* — хороший вариант, но его генератор миграций добавляет ещё один инструмент, а SQL мы всё равно пишем руками ради CHECK-ограничений. Отклонено.

## Последствия

- (+) Нет нативных бинарников и загрузок при сборке; e2e-тесты идут на настоящем PostgreSQL.
- (+) DDL в миграции совпадает с docs/05 буквально.
- (−) Типы в `schema.ts` нужно поддерживать вручную синхронно с миграциями. Расхождение ловят e2e-тесты.
