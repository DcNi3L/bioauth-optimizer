# ADR-0009. Единые zod-контракты; все вычисления на сервере

**Статус:** Принято · **Дата:** 04.11.2026

## Контекст

Входы (параметры распределений, факторы, ограничения) валидируются в двух местах: в форме и в API. Расхождение правил — частый источник ошибок. Кроме того, возникает соблазн считать порог прямо в браузере.

## Решение

- Пакет `@bioauth/contracts`: zod-схемы запросов и ответов + выведенные TS-типы. Используются в моделях форм фронтенда (`safeParse` перед отправкой, ошибки показываются у полей), в `ZodValidationPipe` (NestJS), для разбора ответов в `shared/api` фронтенда и для генерации OpenAPI (встроенный `z.toJSONSchema` → Swagger).
- Фронтенд **не** импортирует `optimization-core`: каждый расчёт проходит через API и сохраняется как эксперимент. Сервер — единственный источник правды о результатах.

## Альтернативы

- _class-validator в NestJS + отдельные схемы на фронтенде_ — две копии правил. Отклонено.
- _Расчёт на клиенте с последующим сохранением_ — две точки исполнения и риск расхождения версий ядра. Отклонено.

## Последствия

- (+) Изменение правила валидации делается в одном месте.
- (+) Сквозная типизация: ошибка контракта видна при компиляции обоих приложений.
- (−) Каждый расчёт — сетевой запрос; при задержке < 50 мс это незаметно.
