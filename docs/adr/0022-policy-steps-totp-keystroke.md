# ADR-0022. Код из приложения и ритм набора как шаги политики входа

**Статус:** Принято · **Дата:** 13.11.2026

## Контекст

В v3.3 (ADR-0020) TOTP служил только вторым фактором сотрудника, а ритм набора проверялся в профиле. Политика входа
(`auth_policy`) знала два шага: «лицо» и «passkey». Поэтому участник без камеры не мог войти, а оптимизатор состава
факторов (СРО1, формулы 2–3) выбирал набор из каталога v3.3, который политика не умела исполнить.

## Решение

1. **Шаги политики.** `totp` (без параметров) и `keystroke` с порогом расстояния `τ_kd` (0,2–4) и признаком
   `calibrated`. Политика по-прежнему содержит один или два шага, каждый фактор не более одного раза.
2. **Сессия входа.** `POST /auth/sessions/{id}/totp` `{code}` и `POST /auth/sessions/{id}/keystroke`
   `{events}`. Шаги идут строго по порядку политики. Общие правила сессии сохраняются: 3 неудачи на сессию, блокировка
   логина после 3 неудач подряд. Дополнительно:
   - код проверяется с той же защитой от повтора и блокировкой TOTP (5 кодов). Если TOTP заблокирован, сессия
     завершается;
   - неточный ввод фразы (опечатка, исправление) — `KEYSTROKE_INPUT`: повтор без счёта в блокировку;
   - для неизвестного логина выдаётся фраза по умолчанию, ответ `NOT_ENROLLED` — существование ритма не раскрывается.
3. **amr (RFC 8176).** `otp` — код, `kbd` — ритм набора (нестандартное значение, в RFC 8176 его нет), `mfa` при двух
   шагах. Способ входа в `login_event` — первый шаг (лицо, если оно есть).
4. **Калибровка τ_kd** тем же замкнутым контуром, что и для лица (ADR-0015). Оценка ритма — `s = 1 − d/4` (растёт с
   похожестью), порог `τ_s = 1 − τ_kd/4`. Источники оценок:
   - genuine — принятый ритм в сессии, подтверждённой вторым фактором;
   - impostor — этот же ввод против шаблонов других людей с той же фразой (как перекрёстные оценки лица).

   `POST /calibration/threshold {modality: "keystroke", modelVersion: "keystroke-sm-v1"}` →
   `POST /calibration/propose {keystrokeExperimentId}`.

5. **Измеренный каталог** (`GET /calibration/factors`) включает:
   - `TOTP`: FAR заявленный, 3·10⁻⁶ (окно ±1 шаг); FRR и задержка измерены;
   - `KEYSTROKE`: FAR и FRR по оценкам, как у лица.
6. **Из решения оптимизатора в политику.** `POST /calibration/propose-from-selection {experimentId}` переводит
   оптимальный состав (`FACE`, `PASSKEY`, `TOTP`, `KEYSTROKE`) в шаги. Порядок: сначала биометрия, затем владение.
   Другие коды — `422 UNSUPPORTED_FACTOR`, больше двух факторов — `422 TOO_MANY_STEPS`. Предложение утверждает
   администратор (с повторным подтверждением, ADR-0021).

## Последствия

- Вход без камеры возможен по политикам «ритм + код», «passkey + код» и подобным.
- Дрейф FRR (`drift.service`) по-прежнему считается только для лица. Для ритма он появится, когда накопятся реальные
  попытки.
- Ритм набора остаётся дополнительным фактором: порог по умолчанию 1,1 подобран на синтетике (ADR-0020), реальные
  FAR/FRR нужно измерять на участниках испытаний. Для этого и нужен контур калибровки.
