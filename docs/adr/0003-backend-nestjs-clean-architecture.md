# ADR-0003. Бэкенд: NestJS + Clean / Hexagonal Architecture по модулям

**Статус:** Принято · **Дата:** 04.11.2026

## Контекст

Требование — строгое соблюдение SOLID. NestJS даёт DI-контейнер и модули, но не задаёт слои внутри модуля.

## Решение

Каждый модуль (`threshold`, `factor-selection`, `factor-catalogs`, `score-datasets`, `experiments`, `examples`) разделён на слои:

- **presentation** — контроллеры, Swagger, `ZodValidationPipe`; без бизнес-логики;
- **application** — use cases (один класс = один сценарий, метод `execute`) и **порты** (интерфейсы репозиториев, парсеров);
- **infrastructure** — адаптеры: Kysely-репозитории, потоковый CSV-парсер.

Доменный слой — пакет `optimization-core` (ADR-0002). Привязка порт → адаптер делается в `*.module.ts` через токены (`{ provide: EXPERIMENT_REPOSITORY, useClass: KyselyExperimentRepository }`). Сохранение эксперимента — отдельный `ExperimentRecorder`, который вызывают use cases расчёта (SRP: расчёт не знает о хранении).

Полный DDD с агрегатами и доменными событиями не применяется: доменная модель — это вычисления без жизненного цикла сущностей, а агрегаты были бы церемонией без пользы.

## Альтернативы

- *Классический NestJS (controller → service → repository)*: сервисы быстро разрастаются и смешивают оркестрацию, расчёты и SQL. Отклонено.
- *CQRS-модуль NestJS*: шина команд избыточна для синхронных расчётов. Отклонено.

## Последствия

- (+) Use cases тестируются с заглушками портов без БД; слой доступа к БД заменяем (что и пригодилось — ADR-0011).
- (+) Новый тип расчёта = новый модуль с той же структурой.
- (−) Больше файлов на модуль; это осознанная плата за явные границы.
